# Библиотека на каждом языке

Фреймворк — это не один сборщик и двадцать обёрток над ним. Фреймворк — это
**библиотека на вашем языке**: вы пишете приложение целиком на нём и ни строчки
на чужом.

Между языком и сборкой лежит один договор — **пакет объявления**:

```json
{"oneframework": 1,
 "app":    {"title": "...", "root": "Board", "screens": [...]},
 "types":  { ... },              // свойства типов полей
 "models": [ { ... } ],          // документы моделей
 "views":  [ { ... } ],          // документы видов
 "logic":  [ { "actions": [...] } ]}
```

Библиотека языка умеет ровно одно: напечатать этот JSON. Всё остальное —
схема, база, PWA, APK — делает сборка, и ей безразлично, кто его напечатал.
Форма договора описана в [`oneframework/declaration.py`](../oneframework/declaration.py).

## Что уже есть

| язык | где | как объявляется приложение |
|---|---|---|
| Python | сам фреймворк | `class Note(Model)` / `class Card(View)` |
| JavaScript | [`libs/js`](js) | `model("Note", {...})` / `view("Card", {...})` |
| Kotlin | [`libs/kotlin`](kotlin) | `object Note : Model(...)` / `object Card : View(...)` |

У Kotlin один и тот же файл собирается **дважды**: под JVM — чтобы напечатать
объявление на машине разработчика, и под WebAssembly — чтобы логика работала
на устройстве. Поэтому общая часть библиотеки не знает ни `java`, ни ресурсов,
ни отражения: отражение (оно ищет имена методов) вынесено в `jvmMain`, таблица
типов едет исходником, а обе точки входа — `main()` и экспорт для wasm —
порождаются сборкой. Это переходники между договором и языком, а не часть
приложения.

Все три дают **побайтово одинаковые** документы моделей и видов — это не
намерение, а тест: `tests/test_three_languages.py`.

## Общее знание — данными, а не копиями

Что известно о типе поля (какая колонка, какой виджет по умолчанию, какие
виджеты вообще), лежит в [`protocol/field-types.json`](../protocol/field-types.json)
и читается всеми тремя. Записать это в каждой библиотеке заново значило бы
завести три копии одного правила; копии расходятся — не сразу, а на одиннадцатом
типе поля, который кто-то добавил в питон и забыл в Kotlin. Расхождение при
этом тихое: приложение соберётся, просто у него будет другой отпечаток вида.

Файл порождается интроспекцией питоновских классов полей
(`python3 -m oneframework.protocol`), а совпадение копий с образцом сторожит
тест.

## Чего пока нет, и это честно

**Сборщик написан на питоне.** Он не едет на устройство и ни строчки на питоне
писать не заставляет — но поставить его нужно. Договор выбран именно так, чтобы
сборщик можно было однажды переписать, ничего не меняя в библиотеках языков.

**Всё, что делает кнопка, — вызов метода.** У записи: `record.delete()`,
`record.save()`, `record.open(Card)`, плюс действия самого приложения
(`record.summary()`). У модели: `Note.create(open=Card)`. Удалить много —
тем же методом, просто найдя много: `Note.search(домен).delete()`. Отдельных
`Delete()`/`Save()`/`Create()` в объявлении больше нет; классы действий
остались внутри как то, во что эти методы разворачиваются.

**Действие — это просто метод модели.** Ни декоратора, ни обёртки: поведение
записи у модели одно, и помечать его нечем. Не действия только имена с `_`
(в питоне это и значит «не наружу» — вычисляемые поля пишутся ими) и
`staticmethod`/`classmethod`/`property`. Что методу позволено записать —
выводится (поля своей модели), а не перечисляется. Уточнить можно
(`@action(writes=[details])`), но это прилагательное к методу, а не разрешение
им быть.

**Сторонние библиотеки доезжают до устройства у всех трёх** — и это видно в
самих примерах, а не в отдельных пробниках. Три приложения-заметки считают одно
и то же тремя разными библиотеками из трёх экосистем:
`python-slugify` (PyPI), `lodash` (npm), `commons-text` (Maven). Ответ у всех
один: `4 слов: Полить Цветами Сегодня Утром`.

 У питона --
колёсами Pyodide (`python_packages`). У Kotlin -- с Maven Central: логика идёт
`kotlinc-jvm` в байткод, дальше TeaVM ([probe-teavm.md](../docs/probe-teavm.md)).
У JavaScript -- с npm: файл логики упаковывается на сборке вместе со всем, что
он импортирует, потому что на устройстве его исполняет `new Function`, где нет
ни `require`, ни `import`. Имена пакетов разрешаются от папки самого файла --
как обычно в Node, то есть из `node_modules` приложения.

Тело, написанное прямо в модели, зависимостей иметь не может: у функции,
взятой через `toString()`, импортов нет. Нужна библиотека -- логика пишется
файлом, и это единственная разница.

**Из узлов вида библиотеки умеют подмножество**: строка, поле, кнопка, список.
Чего нет — отказывает вслух, а не рисует похожее.
